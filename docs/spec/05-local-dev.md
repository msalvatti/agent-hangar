# 05 — Local Development & Run Story

Target: **clone → follow README → it runs**, on macOS with Docker Desktop (OrbStack/Colima also work). Every step is a script; `pnpm doctor` explains anything missing. The same parameterisation that makes Conductor work (per-instance DB, ports, names) is the default for everyone — Conductor is a thin layer on top.

## 1. Prerequisites (README "Requirements")

| Tool | Version | Check |
|---|---|---|
| macOS | 13+ | — |
| Docker Desktop (or OrbStack / Colima) | current; Docker Engine API reachable | `docker info` |
| Node.js | 24 LTS | `node -v` (`.nvmrc` / `.node-version` = `24`) |
| pnpm | 11 | `corepack enable && corepack prepare pnpm@11 --activate` (`packageManager` pinned in root `package.json`) |
| Git | 2.40+ | `git --version` |

No global installs beyond these. Postgres and Redis run in Docker.

## 3. Environment model (one set of variables, three ways to get them)

All configuration is read from environment variables, validated with Zod at boot (`packages/core/src/config`). `.env.local` (gitignored) is generated by `pnpm setup`; `.env.example` documents every key.

| Variable | Default (instance `default`) | Purpose |
|---|---|---|
| `AH_INSTANCE` | `default` | Instance name — suffixes everything below. Conductor sets it from `CONDUCTOR_WORKSPACE_NAME`. |
| `AH_PORT_BASE` | `3000` | Base of a 10-port block. Conductor sets it from `CONDUCTOR_PORT`. |
| `WEB_PORT` | `AH_PORT_BASE + 0` | Next.js |
| `POSTGRES_PORT` | `AH_PORT_BASE + 1` | host port mapped to container 5432 |
| `REDIS_PORT` | `AH_PORT_BASE + 2` | host port mapped to container 6379 |
| `POSTGRES_DB` | `agent_hangar_<instance>` | database name |
| `DATABASE_URL` | `postgresql://ah:ah@127.0.0.1:${POSTGRES_PORT}/${POSTGRES_DB}` | Prisma (`127.0.0.1`, not `localhost`, to avoid macOS IPv6-first resolution hitting a non-forwarded port) |
| `REDIS_URL` | `redis://127.0.0.1:${REDIS_PORT}` | BullMQ + Streams |
| `COMPOSE_PROJECT_NAME` | `agent-hangar-<instance>` | isolates compose containers, volumes, networks per instance |
| `MASTER_KEY_PATH` | `~/.agent-hangar/master.key` | secrets master key (shared across instances is fine; DBs differ) |
| `WORKSPACE_IMAGE` | `agent-hangar/workspace:dev` | image used by the runner |
| `WORKSPACE_NAME_PREFIX` | `ah-ws-<instance>-` | container names/labels → GC only touches its own instance |
| `WORKSPACE_IDLE_TTL_MIN` | `30` | idle GC |
| `WORKER_TURN_CONCURRENCY` | `2` | parallel chat turns |
| `OPENAI_MODEL` | `gpt-5.6-sol` | model id sent to OpenAI |
| `OPENAI_BASE_URL` | unset | optional override (tests point it at a fake) |
| `AGENT_MODEL_PROVIDER` | `openai` | `fake` in E2E |
| `DOCKER_HOST` | unset | optional; runner falls back to `~/.docker/run/docker.sock`, then `/var/run/docker.sock` |
| `LOG_LEVEL` | `info` | pino |

Secrets (PAT, OpenAI key) are **not** environment variables of the web/worker — they live encrypted in Postgres and are entered in Settings. The README says so explicitly.

## 4. First-run experience (what the README instructs)

```bash
git clone <repo-url> agent-hangar && cd agent-hangar
corepack enable
pnpm setup          # 1. installs deps  2. writes .env.local  3. creates master key  4. docker compose up -d  5. prisma migrate deploy  6. builds workspace image  7. runs doctor
pnpm dev            # web + worker with hot reload (turbo / concurrently), prints http://localhost:3000
```

Then in the browser: **Settings → paste GitHub PAT and OpenAI API key → New chat → choose repository → prompt.**

`pnpm setup` is idempotent. What each step does:

1. `pnpm install --frozen-lockfile`
2. `infra/scripts/env.sh` → computes the table above from `AH_INSTANCE`/`AH_PORT_BASE` (or Conductor vars) and writes `.env.local` if absent (never overwrites without `--force`).
3. `infra/scripts/setup.sh` → `mkdir -p ~/.agent-hangar && [ -f master.key ] || openssl rand -hex 32 > master.key && chmod 600`.
4. `docker compose -f infra/docker-compose.yml --env-file .env.local up -d --wait` (healthchecks on both services).
5. `pnpm --filter @agent-hangar/core prisma migrate deploy` (+ `prisma generate`).
6. `docker build -t $WORKSPACE_IMAGE infra/workspace` (multi-stage; bundles `packages/agent-runtime`).
7. `pnpm doctor`.

`pnpm doctor` prints a table: Node/pnpm versions, Docker socket found at …, Postgres reachable, Redis reachable, migrations applied, workspace image present, master key present (0600), secrets configured (✓/✗ with last4), OpenAI model reachable (only if key set). Each ✗ comes with the exact command to fix it.

Other scripts:

| Script | Does |
|---|---|
| `pnpm dev` | `concurrently` web (`next dev --port $WEB_PORT`) + worker (`tsx watch`) |
| `pnpm build` · `pnpm start` | production build/start of both apps |
| `pnpm infra:up` · `infra:down` · `infra:reset` | compose lifecycle (`reset` drops volumes) |
| `pnpm infra:image` | rebuild workspace image |
| `pnpm db:migrate` · `db:studio` · `db:prune` | Prisma |
| `pnpm test` · `test:integration` · `test:e2e` · `test:mutation` | see [06](06-testing.md) |
| `pnpm lint` · `typecheck` · `format` | gates |
| `pnpm ws:list` · `ws:reap` | list / destroy workspace containers of this instance (debug aid) |

## 5. docker-compose services

```yaml
# infra/docker-compose.yml (sketch)
name: ${COMPOSE_PROJECT_NAME}
services:
  postgres:
    image: postgres:18-alpine
    environment: { POSTGRES_USER: ah, POSTGRES_PASSWORD: ah, POSTGRES_DB: ${POSTGRES_DB} }
    ports: ["127.0.0.1:${POSTGRES_PORT}:5432"]
    volumes: [pgdata:/var/lib/postgresql]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U ah -d ${POSTGRES_DB}"], interval: 2s, retries: 30 }
  redis:
    image: redis:8-alpine
    command: ["redis-server", "--appendonly", "yes"]
    ports: ["127.0.0.1:${REDIS_PORT}:6379"]
    volumes: [redisdata:/data]
    healthcheck: { test: ["CMD", "redis-cli", "ping"], interval: 2s, retries: 30 }
volumes: { pgdata: {}, redisdata: {} }
```

Web and worker run **on the host** (fast reload, direct Docker socket access). Workspace containers are created by the worker via dockerode, not by compose. A `profiles: [full]` variant that containerises web+worker (socket mounted read-only) is documented for parity checks but is not the default.

### Workspace image (`infra/workspace/Dockerfile`)

- Base `node:24-bookworm-slim`; installs `git`, `ca-certificates`, `ripgrep`, `jq`, `python3`, `build-essential` (common repo needs); `corepack enable` (pnpm/yarn available).
- Non-root user `agent` (uid 1001), `WORKDIR /workspace`, owned by `agent`.
- Copies the esbuild bundle of `packages/agent-runtime` to `/opt/agent-runtime/` plus `askpass.sh` (`echo "$GITHUB_TOKEN"`) and `git` config: `credential.helper=""`, `user.name/email` from env defaults.
- No secrets, no `.env`, no source of this repo other than the runtime bundle. `ENTRYPOINT ["sleep","infinity"]` — the container idles; the worker `exec`s turns into it.

## 6. Conductor integration (bonus, designed in from the start)

Conductor creates a git worktree per workspace under `~/conductor/workspaces/agent-hangar/<name>`, exposes `CONDUCTOR_WORKSPACE_NAME`, `CONDUCTOR_PORT` (first of a block of 10 ports), `CONDUCTOR_ROOT_PATH`, and runs the repo's setup/run/archive scripts. Because the whole local stack is already keyed by `AH_INSTANCE` + `AH_PORT_BASE`, the integration is three lines of mapping.

```toml
# .conductor/settings.toml  (committed; current Conductor config format — conductor.json is legacy)
"$schema" = "https://conductor.build/schemas/settings.repo.schema.json"

[scripts]
setup   = "./infra/scripts/setup.sh"     # AH_INSTANCE=$CONDUCTOR_WORKSPACE_NAME AH_PORT_BASE=$CONDUCTOR_PORT derived inside
run     = "./infra/scripts/run.sh"       # pnpm dev on the derived ports; prints the URL
archive = "./infra/scripts/archive.sh"   # compose down -v for this instance; reap ah-ws-<instance>-* containers
run_mode = "concurrent"
```

`infra/scripts/env.sh` resolution order: explicit `AH_INSTANCE`/`AH_PORT_BASE` → `CONDUCTOR_WORKSPACE_NAME`/`CONDUCTOR_PORT` → `default`/`3000`. Instance names are slugified (`[a-z0-9-]`, max 30 chars) because they become Postgres DB names and container names.

What is isolated per Conductor workspace:

| Resource | Isolation key |
|---|---|
| Postgres database | `agent_hangar_<instance>` (separate compose project ⇒ separate server + volume too) |
| Redis | separate container + volume per compose project (`COMPOSE_PROJECT_NAME`) |
| Ports | `CONDUCTOR_PORT+0/+1/+2` |
| Workspace containers | name prefix + labels `ah.instance=<instance>`; GC filters by label |
| `.env.local` | per worktree (gitignored; Conductor "files to copy" not needed because setup regenerates it) |
| Master key | shared (`~/.agent-hangar/master.key`) — intentional: same user, secrets re-entered per DB anyway |

Free-tier Conductor is sufficient (local workspaces, bring-your-own agent). The README has a "Working with Conductor" section: open repo in Conductor → New workspace → it runs setup automatically → click Run → open the printed URL. Two workspaces side by side show different ports and different DB names in `pnpm doctor`.
